# Боты, память, оркестратор и инструменты

Как устроены агенты в досках Potok, почему именно так и что делать дальше.

## Модель и провайдер

Один клиент — `services/llm.ts` — для любого OpenAI-совместимого API
(`/chat/completions`). По умолчанию OpenRouter; в настройках можно указать другой
адрес: Groq (`https://api.groq.com/openai/v1`), Gemini
(`https://generativelanguage.googleapis.com/v1beta/openai`), OpenAI, локальную модель
(LM Studio, Ollama, vLLM). Прежние отдельные интеграции Groq и Gemini удалены. Их
сохранённые ключи при первом запуске переносятся на этот API автоматически
(`migrateProviderSettings`).

Клиент один раз повторяет запрос при ответах 429 и 5xx. Ошибки объясняет по-человечески
(«закончился баланс», «модель не найдена»). Расход по каждому запросу записывается.

Поле «модель для служебных задач» (`memoryModel`) позволяет отдать сводки, планы и
проверки более дешёвой модели.

## Ход бота

`services/boardAgent.ts → runBotTurn`:

1. **Память** (`loadTurnMemory`) — сводка канала, до трёх подходящих заметок и окно
   из последних сообщений.
2. **Инструменты** — встроенные `memory_remember` и `memory_recall`, плюс все
   MCP-серверы бота (их может быть несколько). Если инструментов больше 12, отдаются
   12 самых подходящих к запросу (`selectTools`). Иначе описания 40 инструментов
   Pipedream съедали тысячи токенов на каждый запрос.
3. **Цикл** — до 4 раундов вызова инструментов, затем обязательный текстовый ответ.
   Независимые вызовы одного раунда выполняются параллельно. Одинаковый вызов с
   одинаковыми аргументами берётся из кэша хода. Кривой JSON аргументов возвращается
   модели как ошибка, чтобы она повторила вызов.
4. **Политика** `off / ask / auto`. В режиме `ask` каждый внешний вызов требует
   подтверждения; инструменты памяти подтверждения не требуют.

## Память

Раньше каждый ход отправлял последние 20 сообщений целиком: в совещании это
20 × ходы × раунды инструментов. При этом всё старше 20 сообщений забывалось.

Теперь три уровня, от дешёвого к дорогому (`services/memoryCore.ts`,
`services/agentMemory.ts`):

| Уровень | Что | Где | Цена на ход |
|---|---|---|---|
| Окно | до 6 последних сообщений, каждое ≤ 900 символов, всего ≤ ~1500 токенов | в запросе | фиксированная |
| Сводка | всё, что старше окна, свёрнуто в текущую сводку канала (≤ 1600 символов) | `boards/{b}/channels/{c}/memory/summary` | ~300–500 токенов |
| Заметки | долговечные факты, решения, итоги задач; поиск по релевантности (BM25 с лёгким стеммингом) | `boards/{b}/notes` | 0–3 заметки |

- **Сжатие** (рекурсивная суммаризация) запускается, когда за окном накопилось
  8 новых сообщений. Это один дешёвый запрос на 8 сообщений, после чего они больше
  никогда не отправляются. Параллельные вкладки не перетирают друг друга: запись
  идёт в транзакции и проходит, только если сводку за это время никто не обновил.
- **Чтение**: ход читает из Firestore только сообщения новее сводки
  (`getMessagesSince`), то есть единицы документов при любой длине канала.
- **Заметки** пишут сами боты (`memory_remember`), суммаризатор (попутно найденные
  факты) и оркестратор (итог задачи). Люди могут править их в панели «Память».
- **Кэш промптов**: стабильная часть (персона → правила → память) идёт первой, задача —
  последней. Так провайдеры с кэшированием префикса (OpenAI, DeepSeek, Anthropic через
  OpenRouter) не пересчитывают её каждый раз.

Итог: контекст хода ограничен примерно 2–3 тыс. токенов вне зависимости от длины
канала, и бот помнит решения, принятые сотни сообщений назад.

### Что можно сделать дальше
- **Эмбеддинги** вместо BM25 — поиск по смыслу, а не по словам. Нужен endpoint
  `/embeddings` (OpenAI, Voyage, или локальная модель) и хранение векторов у заметок.
  Для сотен заметок на доску BM25 пока достаточно.
- **Иерархические сводки**: сводка по дням или темам поверх текущей, когда каналу
  больше года.
- **Сжатие вывода инструментов внутри хода**: результаты старых раундов
  заменяются кратким пересказом.

## Оркестратор

`services/orchestrator.ts`, `services/orchestratorCore.ts`. Схема «план → исполнение →
проверка» с супервизором:

1. **План** — один запрос: цель, 2–4 проверяемых критерия, шаги. Каждый шаг
   назначается боту по его роли и реально подключённым инструментам: оркестратор
   заранее подключается к их серверам и видит названия инструментов.
2. **Шаг** — бот получает конкретное задание со своим номером шага и работает
   обычным ходом (память, инструменты).
3. **Проверка** после каждого шага (дешёвый запрос): прогресс 0–100 %, какие критерии
   выполнены, нужна ли корректировка. «Готово» засчитывается, только если выполнены
   все критерии. Супервизор может заменить следующий шаг своим.
4. **Итог** — готовый результат, «Степень выполнения: N %» и чек-лист критериев.
   Итог сохраняется в заметки.

Потолок стоимости виден до запуска: `1 + шаги × (запросы хода + проверка) + 1`. На деле
выходит меньше: оркестратор останавливается, как только цель достигнута. В проверке он
пропустил ненужный третий шаг.

Режим «По кругу» (фиксированное число ходов каждого бота) оставлен для обсуждений
без конкретного результата.

### Что можно сделать дальше
- **Параллельные шаги**: независимые шаги плана (сбор данных из разных источников)
  выполнять одновременно.
- **Бот-критик** как обязательный последний шаг для задач с высокой ценой ошибки.
- **Серверный запуск**: сейчас всё работает во вкладке того, кто начал. Для долгих
  задач нужна очередь в Cloud Functions или воркере (потребует тарифа Blaze или
  переноса ключей на сервер).

## Инструменты, контейнеры и браузер

Бот может работать с любым MCP-сервером:

- **Удалённые серверы с CORS** подключаются напрямую: `mcp.deepwiki.com`,
  `mcp.linear.app`, `api.githubcopilot.com/mcp`, а также Pipedream через воркер.
- **Локальные программы и Docker-контейнеры** — через мост `scripts/mcp-bridge.mjs`.
  Он запускает stdio-сервер и отдаёт его по HTTP на `127.0.0.1`:

```bash
# загрузка страниц (официальный образ mcp/fetch)
npm run bridge -- --port 8931 -- docker run -i --rm mcp/fetch

# встроенный браузер: Playwright, Chrome без окна, 25 инструментов
npm run bridge -- --port 8932 -- npx -y @playwright/mcp@latest --headless --browser chrome --isolated

# файлы проекта в контейнере
npm run bridge -- --port 8933 -- docker run -i --rm -v "%cd%:/work" mcp/filesystem /work
```

Мост печатает адрес и токен. Адрес `http://127.0.0.1:<порт>/mcp` указывается у бота
(«Создать бота» или ✎), токен — в «Настройки → MCP-токены» для этого адреса. Кнопка
«Проверить инструменты» сразу показывает, что сервер отвечает.

**Безопасность моста.** Любая открытая вкладка браузера может обращаться к
`127.0.0.1`, поэтому мост:
- принимает запросы только от сайта Potok и локальных dev-серверов (`--origin`);
- требует токен;
- слушает только loopback-интерфейс.

Для браузера и оболочки используйте политику «С подтверждением»: у Playwright есть
`browser_run_code_unsafe`.

Проверено: `mcp/fetch` в Docker загрузил example.com по запросу бота из доски.
Playwright открыл страницу в headless-Chrome.

## Бот из описания

«Создать бота → Создать по описанию»: одна строка описания превращается в имя
(пригодное для @упоминания), полноценный системный промпт (роль, порядок работы,
запреты, формат ответа) и подсказку, какие инструменты нужны. После создания промпт и
инструменты можно менять кнопкой ✎.

## Проверка без ключа и без продакшена

`npm run emulators`, `npm run mock:llm`, `npm run dev:test` — подробнее в README. Мок
понимает запросы сводки, плана, проверки, итога и генерации бота, вызывает
инструменты и помечает в ответе «помню сводку / вижу заметки / контекст: N сообщ.».
По этим пометкам видно, что память работает.

## Пауза в шаге, облачный браузер, OAuth-коннекторы, сохранение кода, советник

- **Пауза**: в задаче оркестратора бот может вызвать `wait_and_resume(seconds, note)` —
  например, пока рендерится видео. На сервере это долговечный `step.sleep`, в браузере
  таймер; потом тот же шаг возвращается тому же боту с пометкой, что проверить.
  До 4 пауз на шаг, от 30 с до 30 мин.
- **Облачный браузер**: `POST {воркер}/tools/browser` — MCP на Cloudflare Browser Rendering
  (`browser_open`, `browser_extract`, `browser_search`). Доступен всем пользователям,
  в том числе в серверных задачах; вход — Firebase-токеном пользователя.
- **OAuth MCP-серверы** (Higgsfield, Notion, Linear и любые по спецификации MCP):
  `/oauth/start` → вход у провайдера → `/oauth/callback`; токены каждого пользователя
  лежат зашифрованными в KV и обновляются сами. Боту даётся адрес
  `{воркер}/connect/mcp?server=<url>`. Higgsfield в Pipedream нет — поэтому так.
- **Сохранение кода**: 💾 у сообщения с кодом — в папку на компьютере (системный
  диалог, Chrome/Edge), скачать, в облако доски (R2) или в GitHub (токен пользователя).
- **Советник по инструментам** (🧩 в окне совещания): оркестратор сравнивает задачу,
  ботов и доступные коннекторы (облачные, OAuth, подключённые и найденные в каталоге
  Pipedream) и предлагает подключить инструмент боту, создать бота по промпту или
  сгенерировать свой MCP-сервер (Cloudflare Worker) — код сохраняется тем же окном.

## Песочницы и Google Cloud Run — на ключах каждого пользователя

- **E2B / Daytona** (`{воркер}/tools/sandbox?provider=…`): ключ пользователь сохраняет
  в Настройках; воркер проверяет его у провайдера и хранит зашифрованным в KV.
- **Cloud Run** (`{воркер}/tools/cloudrun`): пользователь загружает JSON-ключ
  сервисного аккаунта своего проекта и выбирает регион. Инструменты бота:
  `cloudrun_deploy_image`, `cloudrun_deploy_files` (исходники → Cloud Storage →
  Cloud Build: Dockerfile или buildpacks → Artifact Registry → Cloud Run),
  `cloudrun_deploy_github` (публичный репозиторий), `cloudrun_build_status`,
  `cloudrun_service_status`, `cloudrun_list_services`, `cloudrun_delete_service`.
  Сборка идёт минуты — в задаче оркестратора бот ставит `wait_and_resume` и проверяет
  статус. Роли сервисного аккаунта: Cloud Run Admin, Cloud Build Editor, Storage Admin,
  Artifact Registry Administrator, Service Account User; API: run, cloudbuild,
  artifactregistry, storage. Удаление сервиса необратимо — политика «С подтверждением».
